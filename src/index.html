Venora A plugin manager and plugin API for Fermo.

Extend Fermo with plugins without handing each one the run of your client. Every plugin runs in its own sandbox and can only ask Venora to act, through permissions it declared up front.

Install Venora View on GitHub

Fermo is a third-party web client for Spacebar. Venora is an independent browser extension for the Fermo web client at {{ fermoHost }}. It is not made or endorsed by Fermo or Spacebar.

01 What Venora does

Plugins for Fermo, with a boundary around each one.

Venora adds a Plugins page to Fermo's settings and a runtime that keeps plugin code apart from the client. Plugins get a small API instead of the whole page.

Manage plugins

Install a plugin from a ZIP file, then enable, disable, configure, update or uninstall it from Fermo's settings.

Run them apart

Every plugin, bundled ones included, runs in a dedicated worker inside its own sandboxed frame. It has no direct access to Fermo's page, your storage or the network.

Build on API v{{ apiVersion }}

A small, versioned plugin API for notices, settings, storage, mention avatars and events. It is written down as a specification, and tests check the code against it.

02 Plugins

From ZIP file to running, and back out again.

Everything happens in Settings → Plugins inside Fermo. Nothing is stored until a plugin passes every check.

  1. 1

    Install

    Choose Add plugin and pick a ZIP. Venora validates the manifest, permissions, settings, compatibility and file sizes before anything is saved.

  2. 2

    Review

    Every plugin's declared permissions are listed. If it asks for a sensitive one, you have to confirm a warning first.

  3. 3

    Configure

    Plugins can declare settings: switches, text, numbers and choices. Venora draws the settings dialog and only you can change the values.

  4. 4

    Update

    Add a newer ZIP of the same plugin. You see the old and new versions and the release notes, and your settings and data carry over.

  5. 5

    Remove

    Disable a plugin, or uninstall an imported one. Uninstalling deletes its files, settings and stored data.

Updates are manual for now. There is no plugin registry and Venora does not check for new versions. All plugin-management features

04 Sandboxed by design

Plugin code runs several layers away from Fermo.

Each plugin gets its own sandboxed extension frame with an opaque origin and a content security policy of default-src 'none'. Inside it, the plugin runs in a dedicated worker with no window, document or navigable location.

The plugin reaches Venora through a private message port. Only copies of plain data cross it. Venora decides which plugin is asking from the port a request arrives on, never from the request itself.

05 Permissions

Declared up front. Checked on every call.

A plugin lists its permissions in plugin.json. They are fixed for that version, and every request is checked against them. A missing permission means permission_denied, whatever the plugin sends.

storage

Storage

Read its own settings, and keep its own data in a private store.

Standard
ui

Interface changes

Show short notices, apply its declared CSS, and decorate mentions with avatars.

Standard
network

Network access

Lets Venora make a web request on the plugin's behalf, inside a capability that needs it. The plugin cannot send its own requests.

Sensitive
account

Fermo account access

Lets Venora use your signed-in account on the plugin's behalf. The plugin never receives the token or your account record.

Sensitive

Sensitive permissions must be confirmed in a warning at install, and again at every update that declares them. In API v1 they are consent markers: no capability gives a plugin general network access or your account data. Today they unlock only the avatar lookup.

06 Session token

Your token stays yours.

Some things need your Fermo session, such as looking up an avatar. Venora does that work itself, inside its trusted code, and gives the plugin only the outcome: {shown: true}, not the avatar URL and never the token.

As a backstop, every message Venora sends to a plugin passes through one function that checks it against your current session tokens, for every Fermo account in the browser profile. A response containing a token becomes sensitive_data_blocked. An event containing one is dropped. If the tokens cannot be read, nothing is sent.

07 Runtime protection

One misbehaving plugin shouldn't take the rest down.

Each running plugin has its own resource account. These are the limits Venora enforces today, taken from the API v1 specification.

64requests waiting for an answer, per plugin
120 then 60/srequests at once, then a steady rate. Over that: rate_limited
30 sbefore an unanswered capability times out and frees its slot
2 s · 5 swatchdog: a ping every 2 s, and a plugin that hasn't answered in 5 s is stopped
100 then 50/sevents delivered to a plugin. Events over that are dropped
1M charsof strings and keys per message, and 50,000 values. A larger message stops the plugin
1 MiBof storage per plugin: up to 1,000 keys, 64 KiB per value
3 strikesstopped for misbehaviour 3 times, a plugin stays off until the page reloads

Safe mode and recovery. If a plugin makes Fermo hard to use, click the Venora button in the browser toolbar. That menu is outside Fermo's page, so plugin CSS cannot hide it. Turn on safe mode to stop every imported plugin, or disable or uninstall one. Open Fermo tabs apply the change at once.

What isn't capped. Browsers give extensions no way to limit one worker's CPU time or memory. The watchdog stops plugins that stop responding, but a plugin that stays responsive can still use CPU and memory in its own worker.

08 Developer API

A plugin is a manifest and one ES module.

Your default export receives a frozen venora object. Every method returns a promise, takes one plain object, and maps to exactly one permission-checked capability.

  • venora.uiShort plain-text notices
  • venora.settingsRead your declared settings
  • venora.storageYour own key–value data
  • venora.mentionsAvatars beside @mentions
  • venora.onsettings.changed, mentions.added

export default async (venora) => {
  const greeting = await venora.settings.get({key: "greeting"});
  await venora.ui.toast({message: greeting});

  const unsubscribe = await venora.on("settings.changed", ({key, value}) => {
    if (key === "greeting") venora.ui.toast({message: value});
  });

  // Data the plugin keeps for itself, separate from the user's settings.
  const runs = ((await venora.storage.get({key: "runs"})) ?? 0) + 1;
  await venora.storage.set({key: "runs", value: runs});

  return () => {
    // Cleanup. Venora removes what it added to the page for this plugin.
    unsubscribe();
  };
};
